# UI motion for the web dashboard (research, 2026-11-17)

Feeds: which small motion additions to make to the dashboard (not an overhaul).
Source tags: **[S]** = stated by the cited primary source; **[I]** = my inference; **[?]** = not verified this session.

## Q1. Design systems: durations, easing, what animates

### What should and shouldn't animate (sources say)

- **M3:** "standard" is "Material's basic motion scheme for utilitarian UI elements and recurring interactions"; "expressive" is "for prominent UI elements and hero interactions" [S] https://developer.android.com/reference/kotlin/androidx/compose/material3/MotionScheme.md.txt. Spatial springs are for "animations that may change the shape or bounds"; effects springs are for colour and alpha, so those get no overshoot ("non-spatial") [S] same URL. Token values: https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md, https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/MotionTokens.kt, …/ExpressiveMotionTokens.kt, …/StandardMotionTokens.kt
- **Fluent 2:** enter/exit "commonly used for menus, dialogs"; elevation for button states; at the top level "use a quick fade transition instead of moving or sliding UI elements"; "Give larger elements more time to animate than smaller elements"; "Keep the motion constrained to the element in focus"; include a "no motion" setting [S] https://fluent2.microsoft.design/motion. Tokens: https://raw.githubusercontent.com/microsoft/fluentui/master/packages/tokens/src/global/durations.ts, …/curves.ts
- **Carbon:** productive motion for "button states, dropdowns, revealing extra information, and rendering data tables and visualizations"; expressive "for occasional, important moments" (opening a new page, a primary action). Exit easing only for things that leave for good (a closing modal) [S] https://carbondesignsystem.com/elements/motion/overview/
- **Apple HIG:** "Add motion purposefully … Don't add motion for the sake of adding motion"; "Aim for brevity and precision in feedback animations"; "In apps, generally avoid adding motion to UI interactions that occur frequently"; "Let people cancel motion … don't make people wait for an animation"; "Make motion optional" and don't use it as the only carrier of information [S] https://developer.apple.com/design/human-interface-guidelines/motion (read via https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json)
- **NN/g:** for cause and effect, "the effect must begin within 0.1 seconds"; sliding draws attention faster than fading in place; "Animations that are repeatedly encountered are roadblocks to content" [S] https://www.nngroup.com/articles/animation-usability/, https://www.nngroup.com/articles/animation-duration/

### Agree / disagree

- **Agree:** micro-feedback is 50–150 ms; panels and modals are 200–300 ms; little is longer than 400–500 ms. Entering decelerates and exiting accelerates. Frequent interactions get the least motion. Colour and opacity changes never bounce (M3 "effects" springs are critically damped). [S, all of the above]
- **Disagree:**
  - *Curve shape:* M3 and Fluent's main decelerate curve `(0,0,0,1)` is very front-loaded; Carbon's productive curves never fully reach 1 at the end (`.38,.9`), a softer "snap" [S values; I reading].
  - *Physics:* only M3 specifies springs. Fluent and Carbon are duration plus bezier [S].
  - *Exit timing:* NN/g and Carbon give exit its own easing or a shorter time; M3 Expressive's spring model has no separate exit curve [I].
  - *Expressiveness:* M3 Expressive adds bounce (0.6 damping) to "hero" moments. Apple and NN/g push toward restraint on anything recurring [S]. For a stats dashboard opened many times a day, everything except the switch/segmented indicator counts as "recurring" [I].

Sources say:
- **@starting-style + allow-discrete + overlay:** the popover pattern transitions `opacity`, `transform`, `overlay … allow-discrete` and `display … allow-discrete`; the `@starting-style` block "must come after the `:popover-open` rule"; `::backdrop` needs a standalone `@starting-style` block because nesting isn't supported for pseudo-elements; `<dialog>` works the same way [S] https://developer.mozilla.org/en-US/docs/Web/CSS/@starting-style. `overlay` "keeps a dialog or popover in the top layer while it animates out"; since Chrome 130, `@starting-style` rules must come after the normal declarations; a `transition` shorthand declared after `transition-behavior` resets it to `normal` [S] https://developer.chrome.com/blog/entry-exit-animations
- **linear():** values outside 0–1 allow overshoot. The documented way to approximate a curve is to sample it at many points [S] https://developer.mozilla.org/en-US/docs/Web/CSS/easing-function/linear
- **interpolate-size / calc-size():** `interpolate-size: allow-keywords` on `:root` inherits; one end must be a length (two keywords can't interpolate); Chrome 129; browsers without it "get no transition" [S] https://developer.chrome.com/docs/css-ui/animate-to-height-auto, https://developer.mozilla.org/en-US/docs/Web/CSS/interpolate-size. Combining it with `::details-content` is what animates both directions [S, same Chrome article, which predates `::details-content` shipping].
- **Customizable select:** Chrome 135 first; options render in the top layer like a popover, positioned with `anchor()`; parts can be "customized and animated"; "won't break in older browsers". It loses rendering outside the browser pane [S] https://developer.chrome.com/blog/a-customizable-select
- **View Transitions:** the default is a cross-fade; customize it with `::view-transition-old/new(root)`; `view-transition-class` and transition types arrived in Chrome 125; only one transition runs at a time; "the page is frozen" while the update callback is pending; the old view is a screenshot [S] https://developer.chrome.com/docs/web-platform/view-transitions/same-document
- **Anchor positioning:** "available from Chrome 125"; Firefox 147, Safari 26 [S] https://developer.chrome.com/blog/anchor-positioning-api. webstatus.dev reports Chrome 157 / Safari 27 / no Firefox [S] https://api.webstatus.dev/v1/features/anchor-positioning. The likely cause is that web-features re-scoped the feature to include later sub-features [I][?].

**react-router 8 and React 19.3 (important for this repo):**
- React Router's recommended path is now React's `<ViewTransition>` wrapped around `<Outlet/>` in a persistent layout: "Navigations that update the outlet cross-fade its contents." It works in Declarative, Data and Framework modes. "React Transitions must remain enabled … do not set `useTransitions={false}` on your router." Browsers without support "still navigate normally." React "skips view transitions for synchronous updates from `popstate`," so Back/Forward won't animate [S] https://reactrouter.com/how-to/view-transitions
- The `viewTransition` prop on `Link`/`NavLink`/`Form`, `navigate(…, { viewTransition })` and `useViewTransitionState` are **deprecated** but still work. They wrap the update in `document.startViewTransition()`. The page says the deprecated APIs "are available in Framework and Data modes" and doesn't say whether they work in Declarative mode. Enabling both implementations "can interrupt animations" [S] same URL.
- `<ViewTransition>` is stable in React 19.3 (Sep 2026) [S] https://react.dev/blog/2026/09/09/react-19-3. Only Transitions, Suspense reveals and `useDeferredValue` activate it; plain `setState` doesn't. "React doesn't automatically disable animations" for reduced motion [S] https://react.dev/reference/react/ViewTransition
- **Repo fact:** `src/web/main.tsx:23` is `<BrowserRouter useTransitions={false}>`, with a comment explaining why: location must follow history at once, so that a redirect landing mid-navigation can't replace the page a click went to. React Router's recommended route-transition path therefore **conflicts with a recorded decision** [S: repo; I: conflict]. Revisiting that is a design fork, not part of a small motion change.

## Q3. Accessibility and performance

Sources say:
- **WCAG 2.3.3 (AAA):** "Motion animation triggered by interaction can be disabled, unless the animation is essential." Motion animation "does not include changes of color, blurring, or opacity" (errata amends this to *not* exclude blurring; the page is inconsistent) [S] https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html. Technique C39's test passes if the motion "is suppressed" or essential. It doesn't address partial reduction [S] https://www.w3.org/WAI/WCAG22/Techniques/css/C39
- **MDN:** the setting asks for an interface that "removes, reduces, or replaces motion-based animations". "Scaling or panning large objects can be vestibular motion triggers." Its worked example *replaces* a scale pulse with an opacity "dissolve". Windows 11 path: Settings > Accessibility > Visual effects > Animation effects [S] https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion
- **web.dev:** remove "all non-essential movement". Options range from dropping decorative effects to redesigning the page. Pattern: motion only inside `@media (prefers-reduced-motion: no-preference)`. Sites that depend on `animationend` should shorten durations rather than use `animation: none` [S] https://web.dev/articles/prefers-reduced-motion
- **Chrome (view transitions):** "a preference for 'reduced motion' doesn't mean the user wants" no motion at all [S] https://developer.chrome.com/docs/web-platform/view-transitions/same-document. React Router's page gives a reduced-motion rule that removes all `::view-transition-*` animation [S] https://reactrouter.com/how-to/view-transitions
- **Fluent:** provide a "no motion" setting [S]. **Apple:** "Make motion optional" [S] (URLs above).
- **Performance:** "restrict animations to `opacity` and `transform`"; avoid properties that trigger layout or paint; use `will-change` "only if you encounter a performance issue" [S] https://web.dev/articles/animations-guide. Animating `width`/`height` on view-transition groups triggers layout each frame [S] Chrome same-document article.

Inferences:
- The current global rule (`* { transition: none !important; animation: none !important; }`) is WCAG-conformant but heavier than it needs to be. It also kills colour and opacity transitions, which aren't "motion" under 2.3.3. A better default under `reduce` is: keep colour/opacity fades (≤150 ms), drop translate/scale/height and springs, and drop the count-up and chart draw entirely [I].
- One trap: the `*` rule doesn't match the `::view-transition-*`, `::backdrop`, `::picker(select)` or `::details-content` pseudo-elements (`*` matches elements only), so each new feature needs its own reduced-motion line [I][?].
- `height`/`block-size` transitions (`::details-content`) are layout animations. They're acceptable for one small panel at a time, not for lists [I from the web.dev rule].

## Q4. Dashboard-specific patterns

Sources say:
- **Loading:** under 1 s, show neither a skeleton nor a spinner; full-page loads under 10 s, use a skeleton; a single module (a dashboard card), use a spinner; over 10 s, show a progress bar. A pulsing or shimmering skeleton "can potentially be distracting, annoying, or even create accessibility problems" [S] https://www.nngroup.com/articles/skeleton-screens/
- **Stagger / sequence:** stagger table content by 20 ms, keeping the total under 500 ms. Order: shell, static content, dynamic data, primary action, then data visualizations last [S] https://carbondesignsystem.com/elements/motion/choreography/
- **Charts:** animating changed marks or axes helps people notice changes, but "you need to highlight the changes in other ways, too" for VoiceOver users and people who turn off animations [S] https://developer.apple.com/tutorials/data/design/human-interface-guidelines/charts.json. Carbon lists rendering visualizations under productive motion [S] Carbon overview.
- **Count-ups:** no primary source read addresses number count-ups [S: silence in NN/g animation-usability, Apple charts, Carbon].

Inferences:
- The local server answers well under 1 s, so the current opacity pulse on `Loading` is right for the rare slow case. Skeletons aren't worth adding [I from NN/g thresholds].
- Count-ups: the number is the information, and a count-up shows wrong intermediate values, delays reading, and repeats on every visit (Apple: "avoid motion on frequent interactions"; NN/g: repeated animations are "roadblocks") [I]. If wanted at all, use one only where a value *changes while you watch* (a new match lands via the events stream). Keep it ≤400 ms and off under reduced motion [I].
- Chart entry: skip a draw-in on every route visit. Animating *data changes* (a filter change morphs bars or lines) is what Apple's guidance supports. Hand-rolled SVG can transition `transform` on bars (`scale` with `transform-origin: bottom`) cheaply; morphing `d` paths needs JS or CSS `d:` (Chromium only [?]) [I].
- Stagger: Carbon's 20 ms / 500 ms cap fits a tile grid's *first* render. On repeat visits it is noise. If used, give it only to the first page load of a session [I].

## Recommended motion tokens for Grindlog

Grounded in the Carbon, Fluent and M3 values above. The spring is M3's standard default spatial spring (0.9/700) sampled into `linear()`; the "bouncy" one is M3 Expressive default spatial (0.8/380, 1.5% overshoot), for the selection indicator only. I rejected Expressive *fast* spatial (9.5% overshoot) as too playful for a recurring control [I].

```css
:root {
  /* durations */
  --dur-1: 100ms;  /* colour/opacity feedback: hover, press, focus (Carbon fast-02 110, Fluent faster 100, NN/g ~100) */
  --dur-2: 150ms;  /* small moves: switch thumb, segmented/tab indicator, popover (Carbon moderate-01, Fluent fast, M3 Short3) */
  --dur-3: 250ms;  /* dialog / details / route crossfade enter (Fluent gentle, M3 Medium1, NN/g 200–300) */
  --dur-exit: 150ms; /* exits are shorter (NN/g, Carbon) */
  /* easings */
  --ease-standard: cubic-bezier(.2, 0, 0, 1);   /* M3 standard; on-screen changes */
  --ease-enter: cubic-bezier(0, 0, 0, 1);       /* M3 standard-decelerate = Fluent decelerateMid */
  --ease-exit: cubic-bezier(.3, 0, 1, 1);       /* M3 standard-accelerate */
  /* M3 standard default spatial spring (damping .9, stiffness 700), settles ~320ms; use with --dur-spring */
  --ease-spring: linear(0, .049, .161, .295, .43, .553, .659, .746, .815, .868, .909, .938, .96, .975, .985, .992, .996, .999, 1);
  /* M3 Expressive default spatial (damping .8, stiffness 380): 1.5% overshoot, ~430ms to settle; selection indicator only */
  --ease-spring-bouncy: linear(0, .052, .17, .316, .463, .597, .712, .804, .875, .927, .963, .987, 1.002, 1.011, 1.014, 1.015, 1.014, 1.012, 1.01, 1.008, 1.006, 1.004, 1.003, 1.002, 1);
  --dur-spring: 320ms;
  --dur-spring-bouncy: 430ms;
}
```

Under `prefers-reduced-motion: reduce` [I]: set the spatial properties (translate/scale/height) to no transition and keep colour/opacity at `--dur-1`. Concretely, replace the global `*` kill-switch with one that zeroes `transition-property` for transform/translate/scale/block-size, plus explicit lines for `::view-transition-*`, `::backdrop` and `::details-content`.

## Prototype verdict (2026-11-17, branch `prototype/motion`)

Chosen by the user on the real pages, from switchable variants:
- **Charts:** draw in once per page load (line strokes in, dots fade, W/L bars grow from the
  midline), then move between old and new values on every later data change. Rejected: static
  (flat), draw-in on every change (tiresome on revisits). Needs the period query to keep the previous
  data while the next loads, or the charts remount and nothing can move.
- **Press:** `scale: .97` on `:active`, `--dur-1`, `--ease-standard`, on buttons and clickable cards.
- **Dialog:** fade + 8px rise, `--dur-3` in / `--dur-exit` out, backdrop fades. Rejected: fade + scale.
- **Selection indicator:** one sliding element per group on the bouncy spring (`--ease-spring-bouncy`,
  `--dur-spring-bouncy`): header nav, Recap Overview / Matches & numbers tabs, the match rail (vertical),
  and the By date / By match toggle. Rejected: instant, standard spring.
- **Page transitions:** only `<main>` animates; header and tab bars stay live so their indicators keep
  sliding. Route changes (path changes) **rise** (old fades out 90ms, new fades in rising 8px over
  `--dur-3` after 60ms); filter changes (same path, new query) **crossfade** (150ms out / 250ms in).
  Rejected: one style for both (rise on filters felt like too much), fade-through.
  Mechanism: `useTransitions={false}` stays; App keeps a copy of the location that follows the
  router's inside `document.startViewTransition(() => flushSync(...))` and renders
  `<Routes location={copy}>` (see 2026-11-17-route-view-transitions.md).
- **Race check:** the shell e2e "a header click while the start page's redirect is pending is kept"
  passed 20/20 with crossfade and 30/30 with the chosen route-rise/filter-crossfade mix (it failed 4/10
  before `4531ee4`). The remaining ~1-frame gap is closed deterministically by the BACKLOG
  `window.location` redirect check, to be built with this work. Timeouts were considered and rejected:
  a delay moves the gap, it doesn't close it.
